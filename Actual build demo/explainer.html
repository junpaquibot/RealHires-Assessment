How HireIntercept is built, and how to take it live

A plain-language guide to the prototype: what each part does, how the parts connect, and what it would take to run this as a real app for the Real Hires team. Numbers marked Live come straight from the running code.

How it fits together

Three files go in, one function runs every rule in order, and the dashboard shows the result.

1 · InputJob postings, candidates and campaign events (CSV files today; Apollo and Finally Staff later).
2 · ProcessingThe rules engine: normalize, deduplicate, check eligibility, match candidates, score, write emails, check every send, track results, apply stop rules.
3 · DashboardThe front-end. It only shows results; it never makes decisions itself.
EmployeeUses the dashboard and decides anything the rules won't decide alone. Every decision re-runs the engine.

In code, all of Processing is one function: pipeline.run(files, decisions). It takes the raw files plus any employee decisions and returns a single snapshot. The product, the simulator and this guide all read that same snapshot, so they can never disagree.

Running and changing it

No install is needed to run it. Node.js is only needed for the extras.

Run

Double-click any HTML file. Everything works offline, from the folder, with the sample data built in.

Test the rules

cd "Actual build demo" node tests/engine.test.js

28 checks: the lead counts, who is eligible, the scores, candidate assignment, drafts, the funnel numbers and the stop rules.

Change a rule

Every weight, keyword and schedule is in js/rules.js. For example, to give candidate fit more weight, change weights.fit and fitPoints.verified. Then reload the simulator: every component updates. Run the tests to see which agreed outcomes would change.

Rebuild the product after a change

node tools/build-product.js # packs index.html into ../App-product.html node tools/embed-data.js # only if you edited data/*.csv

Taking it live

The prototype runs in one browser. A live app needs a server, a database and a background worker, so it keeps working when nobody has it open.

Recommended: TypeScript full-stack

A Node.js backend with Postgres, serving the same dashboard. The prototype's JavaScript modules move to the server almost unchanged, and one language covers the backend, the front-end and the integrations. That keeps the team small and the rules shared.

Web app + APIServes the dashboard and handles employee actions. Behind a company login (SSO).
PostgresLeads, candidates, events, decisions, suppression list and audit log.
Worker + job queueRuns syncs, scoring and follow-ups. Every send job runs the suppression check first.
SchedulerCron jobs: sync postings and candidates, and roll up campaign numbers.
Webhook endpointReceives Apollo events (replies, bounces, unsubscribes) within seconds.
HostingOne PaaS (e.g. Render, Railway or Fly.io) for app, worker and database. Simple to run.

Alternatives

  • Python backend (FastAPI + Postgres): strong if scoring becomes data-science heavy. The cost is that the rules get rewritten and the team works in two languages.
  • Low-code (n8n or Zapier + Airtable): the fastest to stand up. But stop rules, deduplication and audit trails are hard to test, and they get fragile as volume grows.

Path to production

The order that gets value earliest, with the safety rules in place before any real email goes out.

  1. Backend and database. Move the modules server-side unchanged. Store leads, events, decisions and the audit log in Postgres. Keep the tests running in CI.
  2. Login. Company SSO (Google Workspace or Microsoft). Replaces the prototype's demo sign-in.
  3. Read-only integrations. Sync job postings from Apollo and candidates from Finally Staff. No sending yet: just check the leads and matches look right.
  4. Events and suppression. Apollo webhooks into the events table, and a suppression list synced both ways. Prove the stop rules work on real data.
  5. Sending, gated. Approved drafts go to Apollo sequences through the worker. Every send runs the suppression check first. Start with a small daily cap.
  6. Measure. Grow the A/B test until each variant has enough emails to compare honestly.
  7. Monitoring. Alerts if a sync fails, bounces rise, or a send happens without a passing check.

Real integrations

Apollo (leads, contacts, sequences)

  • API key kept on the server, never in the browser.
  • Pull: companies and postings on a schedule, plus a real contact per company. This replaces "contact = company domain".
  • Push: approved emails into one sequence per variant, with the variant recorded on our side.
  • Webhooks: sent, delivered, opened, replied, bounced and unsubscribed events, stored once each by event ID.
  • Suppression synced both ways, so an unsubscribe in either system blocks both.

Finally Staff (candidates)

  • Candidate profiles with skills (ideally a shared skills list), available-now with a date, U.S.-hours availability, location and licences.
  • A reservation or status field, so "one candidate, one company at a time" holds in both systems.
  • Consent from candidates before they're mentioned in outreach.

Risks to handle before going live

Technical: the rules read free text

Remote policy, notes and skills are written by people. Keywords like "licensed" or "unclear local restriction", and exact skill names, will miss things like "must live in Texas" or "QBO" vs "QuickBooks". Fix: a skills synonym list, a phrase list for location and licences, tests built from real postings, and "unclear → ask an employee" kept as the default, so misses fail safe.

Commercial: email reputation

The history already shows emails to U.S.-only and unverified companies, and a follow-up to a licensed U.S.-only role. Cold email that ignores eligibility or stop signals gets marked as spam, hurts the sending domain and risks complaints. Fix: a separate warmed-up sending domain, daily volume caps, suppression shared across systems, and today's ⚠ checks made hard gates in the send path.

What's simplified in the prototype

  • Nothing is sent. Drafts are shown only, and the integrations are replaced by CSV files.
  • Decisions and the audit log live in this browser, not a database.
  • The sign-in on App-product.html is a demo gate (admin / admin), not real security.
  • One follow-up schedule for everyone, taken from the history: email 2 three days after email 1.
  • The A/B test is too small to read (about 13 emails each). The dashboard says so.
  • Simulated events in the simulator only affect stop rules. They never change the campaign numbers.
