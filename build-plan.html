Step 1 · If this were an actual app

These would be its individual components

A hosted web app with a backend. Real data comes in from Apollo, Finally Staff and the email provider. Rules run on the server, and a scheduler sends follow-ups only after checking the stop rules.

Step 2 · But this is a 5-hour prototype

So it's a local app that runs on any computer

"I'm keeping the same components, but running them all in the browser. It opens with a double-click, needs no install or keys, and still ticks off every requirement."

Runs anywhere

Only needs a web browser. No Python, no Node, no command line on the reviewer's machine.

Same components

One file per component, matching the real-app boxes above. Moving to a server later is a relocation, not a rewrite.

Safe by design

Synthetic data only. No live email, scraping, paid keys or real Apollo records, as the brief requires.

Easy to demo

Opens offline from the repo, or from a free static host for a shareable demo URL.

Step 5 · If we took it live

The most effective way to build the real thing

TypeScript full-stack Recommended

Node backend, Postgres, the same UI. The prototype's JavaScript modules move to the server nearly as-is, and one language covers backend, frontend and integrations.

Python backend

FastAPI + Postgres with a separate web frontend. A strong choice if scoring later becomes data-science heavy, but the rules would be rewritten from JavaScript and the team works in two languages.

Low-code automation

Workflow tools plus a spreadsheet-style database. The fastest to stand up, but stop rules, deduplication and audit trails are hard to test and easy to break as volume grows.

Path to production

  1. Backend + database: move the modules server-side; store leads, events, suppressions and the audit trail in Postgres.
  2. Real connectors: replace the CSV sources with Apollo and Finally Staff adapters that keep the same output shape. API keys live only on the server.
  3. Sending + events: send through Apollo sequences or an email provider; receive delivered/opened/replied/bounced events by webhook instead of CSV.
  4. Scheduler: run follow-ups on a queue that re-checks the suppression list immediately before every send.
  5. People in the loop: login, a review queue for "Verify" jobs, and draft approval before anything goes out.
  6. CI/CD + monitoring: automated tests on every change, then deploy as an installable web app that works on laptop and phone.
